# P360 77→114 audit delta

The 2026-09-14 read-only P360 audit confirms the OpenSpec's clause-completeness direction and adds
one required input: a trusted declaration of the system boundary and each repository's role.

P360 is not one repository. The supplied Connector, Admin API and Workflow API expose only health
routes; the Portal is a starter; the Database holds values and relations; and the code serving the
deployed QA API is not present. A one-snapshot analyzer can truthfully say a handler is absent from
Connector and still be unable to conclude that the deployed system lacks it.

The proposal therefore MUST distinguish:

- `not_found`: searched the complete, declared owning source and found no implementation;
- `contradiction_found`: reached the governed production control and it conflicts with the clause;
- `cannot_tell / snapshot_scope_incomplete`: the owning component is absent or unknown;
- `mentions_only`: a schema/configuration/declaration exists without a visible reachable consumer.

The P360 golden fixture SHALL exclude test code as implementation evidence and include these cases:

1. commented-out inbound/outbound routes in the declared Connector;
2. an OS/device matrix and TTL constants present only as database seed data;
3. Rich-Link and List-Picker SSRF guards seeded `false`;
4. a row associating opaque ID and phone number, with authority/access boundary unresolved;
5. tenant relations present without visible RLS or scoped application queries;
6. a missing deployed implementation repository causing system-level `cannot_tell`.

The historical 77-item mapping is the baseline. The expanded run adds the latest code/mixed-method
items through 114, especially C.14–C.30, H.3, H.4, I.6 and K.1. Non-code and Apple/process rows do
not enter source analysis merely to complete the count. Mixed-method items keep independent code,
API/Postman, UX/device and human results.
